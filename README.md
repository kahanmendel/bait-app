# bait-app

מערכת לניהול וסתות וטהרת המשפחה — Flask + PostgreSQL, רצה על Google Cloud Run.

**Production:** https://bait-app-602446976212.europe-west1.run.app

## מבנה

```
main.py            application factory של Flask
extensions.py      db + login_manager
models.py          User, Veeset, VesetKavua, Reminder, PhoneSession
logic/             חישובי הלכה — עונות, וסתות קבועות, הפלגות, הפסק טהרה, טבילה
routes/            blueprints: auth, dashboard, veeset, settings, reminders,
                   pregnancy, admin, cron, api (JSON), yemot (שלוחות טלפוניות)
templates/         תבניות Jinja
```

## הרצה מקומית

```bash
cp .env.example .env      # ומלא ערכים
pip install -r requirements.txt
python main.py            # http://127.0.0.1:5000
```

בלי `DATABASE_URL` המערכת משתמשת ב-SQLite מקומי (`instance/bait_app.db`).

## זמנים, עונות והתראות

העונה נקבעת לפי הנץ ושקיעה, ולכן דיוק הזמנים הוא דיוק ההלכה. הזמנים
מחושבים **מקומית** ב-[logic/zmanim.py](logic/zmanim.py) דרך `hdate`, בלי שום
קריאת רשת ועם אזור זמן אמיתי (`Asia/Jerusalem`).

עד כאן הזמנים נשלפו מ-`api.sunrise-sunset.org`, וכל כשל נפל בשקט ל-6:00
ו-19:00. נפילה כזו אינה אי דיוק קטן:

```
ירושלים, 17/11/2026:  שקיעה אמיתית 16:40   ברירת המחדל שהייתה 19:00
ראייה ב-17:30 נרשמה עונת יום — בפועל עונת לילה, ששייכת ליום העברי הבא
```

אותה טעות קרתה גם כשה-API הצליח, כי ההמרה ל-UTC הייתה `+3` קבוע ולא
התחשבה בשעון החורף.

### כשאין זמן מדויק

שני מצבים נותרו שבהם אין זמן מדויק: שגיאה בחישוב עצמו, וזמנים ידניים
(`use_auto_times=False`) חסרים או פגומים. בשניהם המערכת **אינה שותקת**:

1. `SunTimes.reliable` חוזר `False`, והראייה נשמרת עם `onah_needs_review=True`.
2. הלוח הראשי מציג בנר אדום עם קישור לכל ראייה שדורשת אימות, ותג בשורה שלה.
   שמירה ידנית של הראייה מנקה את הסימון אם הפעם היו זמנים מדויקים.
3. בשלוחה הטלפונית המתקשרת שומעת "העונה נקבעה בלי זמן מדויק ויש לאמת אותה".
4. נשלחת התראה למייל שמוגדר ב-`ALERT_EMAIL`.

בזמנים ידניים פגומים המערכת משתמשת בזמנים המחושבים למיקום של המשתמשת ולא
בברירת מחדל גסה — אבל מסמנת לאימות, כי אלה אינם הזמנים שהמשתמשת ביקשה.

### ההתראות

[logic/alerts.py](logic/alerts.py) שולח SMTP. ההתראה נשלחת מתוך בקשה חיה,
לפעמים בלב שיחה טלפונית, ולכן:

- **timeout של 5 שניות**, כדי שהתראה לא תתקע שיחה.
- **איחוד לפי מזהה תקלה** — מייל אחד לשעה לכל `key`, דרך טבלת `alert_log`.
  תקלה חוזרת לא מייצרת מייל על כל ראייה. הטבלה בבסיס הנתונים ולא בזיכרון,
  כי ב-Cloud Run יש כמה מכונות והן מתחלפות.
- **אינו זורק חריגות** — תקלה בשליחת ההתראה לא מפילה את הפעולה שעליה היא
  מתריעה, ונרשמת ב-`alert_log` עם `delivered=false`.
- אם ההתראות אינן מוגדרות, זה עצמו נכתב ללוג כ-`ERROR` עם שמות המשתנים
  החסרים — כדי שחוסר הגדרה לא יהפוך בעצמו לשתיקה.

ב-Gmail נדרשת **App Password** ולא סיסמת החשבון, והחשבון חייב 2FA.
`SMTP_PASSWORD` שייך ל-Secret Manager; שאר ההגדרות אינן סודות.

## דוח מנויים

לכל חשבון שלושה מצבים, ב-`User.status`:

| מצב | איך נוצר | `is_approved` | `rejected_at` |
|---|---|---|---|
| `approved` — מחובר | המנהל אישר | `True` | ריק |
| `pending` — ממתין לאישור | נרשם ועוד לא אושר | `False` | ריק |
| `rejected` — נדחה | המנהל חסם | `False` | חותמת זמן |

**עד הוספת `rejected_at` שני המצבים האחרונים היו זהים בבסיס הנתונים** —
`/admin/reject` רק כיבה את `is_approved`, ולכן חשבון שנדחה נראה בדיוק כמו
חשבון שטרם אושר, גם במסך הניהול וגם בהודעה שהמתקשרת שמעה. כעת חשבון שנדחה
שומע בטלפון "החשבון שלך נחסם" ולא "ממתין לאישור", וחשבון שאושר מחדש מנוקה
מהסימון.

`is_approved` נשאר השער בכל הכניסות — באתר, ב-API וב-`/yemot` — ולכן ההפרדה
לא שינתה מי נכנס ומי לא.

### שליחת הדוח

- **כפתור** במסך `/admin`: "שלח דוח מנויים למייל". מציג אם המייל יצא, ואם לא
  — את הסיבה, בלי לחפש בלוג.
- **נתיב** `POST /cron/users-report` (גם GET), מאומת ב-`CRON_SECRET` כמו שאר
  נתיבי ה-cron. מחזיר 200 עם `success` ו-`detail`, או 502 בכשל שליחה כדי
  ש-Cloud Scheduler ינסה שוב.

הדוח מפרט לכל חשבון: שם, שני הטלפונים, סימון מנהל, תאריך הרשמה, תאריך דחייה
אם נדחה, מספר הראיות והאחרונה שבהן, כמה ראיות דורשות אימות עונה, והריון פעיל.

דוח שבועי קבוע:

```bash
gcloud scheduler jobs create http bait-app-users-report \
  --location=europe-west1 \
  --schedule="0 8 * * 0" \
  --time-zone="Asia/Jerusalem" \
  --uri="https://bait-app-602446976212.europe-west1.run.app/cron/users-report" \
  --http-method=POST \
  --headers="Authorization=Bearer <CRON_SECRET>"
```

הדוח משתמש באותה הגדרת SMTP של ההתראות, ולכן שליחה מוצלחת שלו היא גם
האישור שההתראות עובדות.

## ממשקים חיצוניים

| `/api/*` | REST/JSON — אימות ב-`X-API-Key` או `X-Session-Token` |

### הגדרת השלוחה בימות המשיח

בממשק הניהול של ימות, בשלוחה הרצויה:

```ini
type=api
api_link=https://bait-app-602446976212.europe-west1.run.app/yemot
api_add_0=secret=<YEMOT_API_SECRET>
api_phone_send=yes
api_call_id_send=yes
api_did_send=yes
api_wait_answer_music_on_hold=yes
say_api_answer=no
api_log=yes
api_end_goto=/
```

- הסוד עובר ב-`api_add_0` ולא בתוך `api_link`. ימות מצרפת את הפרמטרים שלה
  בסימן שאלה נוסף במקום ב-`&`, ולכן query string ב-`api_link` מגיע מעוות
  (`secret=<הסוד>?ApiCallId=...`). השרת חוסם זאת ממילא, אבל ההגדרה הנכונה
  היא `api_add_0`.
- `api_phone_send=yes` הכרחי — בלי מספר המתקשרת אין זיהוי בכלל.
- `say_api_answer` חייב להיות `no`, אחרת ימות תקריא את הפקודות עצמן במקום
  לבצע אותן. שווה להדליק זמנית רק לדיבוג.
- נקודה היא מפריד בין הודעות, ולכן `logic/yemot.py` מסיר אותה ואת שאר
  התווים האסורים מכל טקסט TTS.
- בכל שדה ב-`read=` נשלח ערך מפורש. שדה ריק באמצע נקרא כאפס, ו-`sec_wait`
  ריק פירושו שהשיחה תתנתק מיד אחרי ההודעה.
- לאבחון: `Log/LogApi.ymgr` בספריית ימות מציג כל בקשה ותשובה, כאשר `=`
  מוצג כ-`^`, `&` כ-`*` ו-`,` כ-`>`.

**שם השדה `re_enter_if_exists` מטעה.** ברירת המחדל `no` גורמת לימות לשאול
את המשתנה מחדש, ואילו `yes` אומר לה להשתמש בערך שכבר נאסף בלי להמתין
להקשה. תפריט שנשלח עם `yes` חוזר מיד עם הבחירה הישנה ויוצר לולאה במהירות
מכונה — זו הייתה תקלת השיחה הראשונה.

לכן:

- **ענף שרק קורא מידע** (2, 3, 4) חוזר לתפריט. המשתנה היחיד המעורב הוא
  `menu` והוא נשאל מחדש, כך שאין מצב שנשאר מאחור.
- **ענף שכותב נתונים** (1, 5, 6) מסתיים בניתוק. אין פקודה מתועדת שמנקה ערך
  שכבר נאסף, וערכי הביניים שלו (`rep_time`, `rem_date`, `set_value`…) היו
  נשארים בשיחה וגורמים לכתיבה נוספת בכניסה שנייה לאותו ענף.
- `MAX_MENU_ROUNDS` עוצר את השיחה אם התפריט חוזר יותר מדי פעמים, כדי
  שקריאה שגויה של הפרוטוקול לא תוכל שוב להפוך ללולאה.

`test_yemot.py` בודק את שלושת הכללים האלה.

ימות מזהה את המתקשרת לפי `ApiPhone`. מספר שרשום כ-`phone` או כ-`phone_husband`
מזדהה בקוד האישי ומקבל תפריט: דיווח ראייה חדשה, ימי פרישה קרובים, פרטי
הראייה האחרונה, תזכורות קרובות, הוספת תזכורת, והגדרות (מנהגים, ימי ספירה,
שעות תזכורת, ושינוי הקוד של המספר שממנו התקשרו).

כותרת תזכורת נבחרת מרשימה קבועה ולא מוקלדת, כי אין דרך אמינה להזין טקסט
עברי מלוח המקשים. להזנה חופשית יידרש מצב `stt` או הקלטה, ששניהם דורשים
הגדרה נוספת בצד ימות.

**ערך שנקרא עם `typing_playback_mode` חוזר מפורמט ולא כספרות גולמיות** —
שעה חוזרת כ-`10-10` ותאריך כ-`01-01-2026`. `_digits()` מסנן כל תו שאינו
ספרה לפני הפענוח.

מספר שאינו מוכר מקבל מסלול הרשמה — בוחר קוד אישי, מקיש אותו פעמיים, והחשבון
נוצר **לא מאושר**. עד שהמנהל יאשר אותו במסך `/admin`, כל שיחה מהמספר הזה
עונה "החשבון שלך ממתין לאישור המנהל" בלי לבקש קוד. הרשמה טלפונית לעולם אינה
מעניקה הרשאות ניהול, כי מזהה מתקשר ניתן לזיוף.

### קודים לשני המספרים

לכל חשבון יש שני מספרים ושני קודים: `pin_hash` לאישה ו-`pin_hash_husband`
לבעל. כל עוד לא נקבע קוד נפרד לבעל, שני המספרים נכנסים עם הקוד המשותף — כך
משתמשים קיימים אינם ננעלים בחוץ. `check_pin_for(phone, pin)` בוחר את הקוד
לפי המספר שממנו נכנסו, ומשמש באתר, ב-API וב-`/yemot` כאחד. שינוי הקודים
נעשה במסך ההגדרות, ואפשר לבטל שם את הקוד הנפרד ולחזור לקוד משותף.
